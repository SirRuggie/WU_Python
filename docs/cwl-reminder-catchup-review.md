# Missed campaign reminder catch-up

A persisted scheduled campaign message that became due during a bot restart is decided before normal restore and schedule reconciliation can replace or delete its original due time. An eligible message is sent once, late, within the single `MAX_CATCHUP_AGE` six-hour window. Equality is eligible at dispatch; preparation that crosses the window is refused. The original destination, role mentions, text and occurrence identity are retained.

This applies only to persisted scheduled jobs for the current campaign cycle, using its configured timezone, with matching generation, activated automation, no pause, and an enabled message and audience. A missing pending job is not recreated from schedule calculations. Manual sends, retries and roster posts retain their existing behavior. Signup and reminder closure uses only the existing campaign deadline, not SQL signup state.

When several eligible messages are overdue, only the newest per Main or Lazy pool remains; older ones receive a skipped history receipt. The native sequence-spacing guard remains authoritative. It can prevent the newest eligible catch-up and records `Skipped: too close to another send`; there is no fallback to an older message and no burst. Any delivery record blocks automatic catch-up. Stale settings, closed signups, rollover, pauses, disabled messages and excess age receive a recorded reason and an existing journal ALERT. No new alert transport, Discord warning, polling loop or recipient is added.

The existing future-only meaning of `schedule_synced` is unchanged. Idle reconciliation after its acknowledgement does not fetch catch-up state.

## Storage and crash boundaries

`utils/cwl_campaign.py` owns the additive persisted state. Existing scheduled pending rows are compare-and-swap tagged with protocol 1 and `original_due_at`, retaining their canonical occurrence ID. New cycle metadata records reported catch-up occurrences, and the existing claim, sent and uncertain sets remain authoritative. A durable uncertain marker is written before entering Discord's POST. Confirmed late receipts retain actual delivery time, original scheduled time and lateness. A failed ledger write stores the confirmed receipt as `ledger_pending` only while the original pending-row identity is still owned; restart recovery is idempotent, including a lost acknowledgement after a successful receipt write. Fallback writes and cleanup compare the observed generation, job kind, original time and status; recovery also matches the confirmed message ID. They cannot overwrite or delete a newer manual/future job or a different receipt. If that ownership changed before a fallback, the existing durable uncertainty marker and an explicit review receipt/journal alert remain; there is no automatic replay. Missing legacy scheduled status is normalized when an existing eligible row is tagged, without deriving a new job.

A protocol-1 claim with no POST-boundary marker can safely resume after a pre-effect crash. An old unversioned claim, malformed existing claim, failed acknowledgement of the POST marker, exception after entering POST, or response without a usable message ID fails closed for staff review. There is no automatic replay of an uncertain effect. Normal manual/retry transport policy is not changed by this feature.

There is no migration or production data rewrite. New storage-owner helpers use indexed `_id` point queries/CAS; the owned Mongo explain uses `_id_` and examines at most one document. The native restore/install already perform global pending-job scans, and the reused `load_campaign` has existing per-guild cycle/recurring-history scans. Those inherited scans remain, so this change does not claim that the complete pre-existing scheduler/loader callgraph is bounded. New per-cycle state reads happen only when persisted catch-up candidates exist. Delivery history remains capped by the existing history limit; catch-up reports are separate from explicit staff skip state so a later ordinary future schedule is not disabled by an automatic old-job decision.

## Staff history

The existing history disclosure uses a small shared history renderer. It shows Main/Lazy, `Sent late` with actual and original scheduled time, plain skipped reasons, `Post deleted` for confirmed deletion, and neutral unavailable labels for unknown values. It renders external text through React text nodes, never raw HTML, and does not fetch or send anything. The retained receipt and payload data are unchanged by this presentation.
